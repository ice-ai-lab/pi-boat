# ADR-0014：一期范围排除与延后（鉴权 / 登录 / 终端 / 内建子代理运行时）

- 日期：2026-01
- 状态：已接受（Accepted）
- 关联文档：`docs/01-overview.md` §9-4a（同内容的工程视图）；`docs/02-protocol-inventory.md` §5.3 / §6.5 / §6.8 / §10；`docs/07-backend-capability-gap.md` §8（排除/延后清单与理由）
- 关联决策：**部分取代 ADR-0007**（其「LAN 场景另议」段落在本文改为明确不做）；ADR-0012（扩展 UI 不引入 TUI 渲染，与终端排除保持一致）

## 背景

一期要对齐既有 Web 实现的后端能力面（`docs/07` §1）。在逐域核对时，有四项能力**被明确决定不做或延后**。
这些决定此前只落在设计文档的正文里（`docs/01` §6 / §9-4、`docs/02` §5.3 / §6.8），**没有可检索的决策落点**。

后果已经出现过一次：终端能力在 2026-01 被从协议里移除（`docs/02` §5.3），同月的复盘中却仍能从
`docs/01` 的架构图、技术选型表、里程碑里读到 PTY / node-pty / xterm —— 因为那次「不做」只是一个文档级别的
编辑，不是一条决策记录。同类能力（尤其鉴权与终端）会被反复重新提出，每次都要重新论证一遍。

因此本文的目的**不是新决策**，而是把已定的四项落成决策记录，并写清推翻它们的代价。

## 决策

四项分别记为**排除（不做）**或**延后（将来以增量方式引入）**，并同时清除全库的残留描述。

### 1. 鉴权（本机访问凭据 / LAN）——排除 ⛔

- 不做：口令登录、session cookie、`Authorization: Basic`、失败节流、`/api/web-auth` 三端点、
  非回环绑定开关、反代外部主机名白名单
- **保留不变**：ADR-0007 的三闸（Host / Origin / Sec-Fetch-Site）与「GET 不得有副作用」。
  三闸挡的是「用户浏览器里的恶意网页」，与「谁可以访问服务」是两件事——排除的是后者
- **连带结果**：`docs/01` §9-4 的局域网访问开关随之排除（LAN 暴露必须凭据，无凭据即不可开）；
  → **ADR-0007 的「LAN 场景另议」段落在本文被取代**（从「另议」改为「不做」）

### 2. 登录（provider 身份认证入口）——排除 ⛔

- 不做：`GET /api/auth/providers`、`GET/POST /api/auth/login/:provider`（OAuth / device-code SSE）、
  `POST /api/auth/logout/:provider`、`POST/DELETE /api/auth/api-key/:provider`
- 按「整个 provider 身份认证入口」理解，**包含**凭据写入（在 Web 里填 API Key 也一并排除）
- **连带结果**：模型凭据一期只经 `GET/PUT /api/models-config`（`models.json` 原文，含 provider 级 `apiKey`），
  或由用户在本机的 `pi` CLI / TUI 配置后由本服务读取；`POST /api/provider-usage/query`（余额查询）
  依赖凭据来源，默认不做
- **恢复成本低**：若日后只想恢复「在 Web 里写 API Key」，加回 `api-key` 两个方法即可，其余不动

### 3. 终端（PTY）——排除 ⛔

- 不做：`POST /api/terminal`、`GET/POST/DELETE /api/terminal/:id`、`GET /api/terminal/:id/events`、
  `TerminalEvent` wire 类型、`node-pty` 依赖、xterm 前端
- **同时不做**：Shell 直连命令组（`bash` / `abort_bash`）与 `GET /api/agent/:id/bash-output`
  ——超长 bash 输出临时文件不提供读取端点
- **保留**：`BashExecutionMessage` 的协议类型与历史渲染。它是 `.jsonl` 里的既有消息角色
  （CLI 里 `!` 执行的记录），属**消息渲染**而非终端执行能力；丢掉它会让既有历史会话缺一段
- **与 ADR-0012 的关系**：扩展 UI 通道因此也不引入 TUI 渲染（`pi-tui`）——两者取向一致

### 4. 内建子代理运行时——延后 ⏸（非排除）

- 一期不做：内联 extension 注册 `Agent` / `get_subagent_result` / `steer_subagent` 保留工具、
  profile 解析与 precedence、worktree 隔离、后台运行与通知去重、子代理标记 custom 条目的写入、
  `/api/subagents/*` 全部端点（settings / profiles / `:id`）、侧栏家族聚簇
- **为什么影响有限**：子代理**不是 SDK 内建能力**，而是某个 extension 注册工具后才存在。本产品用同一套
  SDK 与同一份资源目录，用户自行安装提供同类工具的扩展包即可获得该能力，**后端零改动**
- **保留**：`SessionReadService.delete()` 的子代理标记判定对既有会话文件仍然生效（级联删除不回退）
- **将来引入路径**：以 pi 扩展形式提供（第三方包或自研），协议侧只加不改（新增端点非破坏性）；
  届时再评估是否升级为内建运行时以换取管理面与家族聚簇

### 5. 其他（同批排除）

`GET /api/app-update`（发布通道未定）、Next.js / SSR、非回环绑定的 TLS 与扫码配对、
SQLite / 自建存储、会话列表分页（触发条件驱动，`docs/02` §9-7）。

## 备选方案

| 候选 | 结论 | 理由 |
|---|---|---|
| 拆成四条独立 ADR | ❌ 放弃 | 四份内容同构（「不做 + 连带结果 + 恢复成本」），检索粒度不值得四倍维护成本 |
| 不写 ADR，保持 `docs/01` §9-4a + `docs/07` §8 | ❌ 放弃 | 终端能力的复发表明：只写在设计正文里的「不做」拦不住下一次重新提出。ADR 在这里的唯一价值就是**防重建** |
| 只写 ADR，不动设计文档里的残留描述 | ❌ 放弃 | 会长期留下「文档说要做、ADR 说不要做」的矛盾（终端已发生过一次） |
| 把子代理也记为「排除」 | ❌ 放弃 | 它是**延后**：能力可由扩展提供，协议侧将来只加不改。写成排除会误导后续会话直接否决该方向 |

## 后果

**正面**

- 四项各有可检索的决策落点，含**推翻成本**（鉴权与终端要推翻，需先改本文并同步恢复设计文档）
- 全库残留描述同步清除，`docs/01` / `docs/02` 不再自相矛盾
- 能力面计数随之收敛：路由/handler 目标 ≈55（78 − 23），`docs/07` §1 已按此更新

**负面 / 已知风险**

- **鉴权缺席的代价要反复提醒**：非回环绑定不可用 ⇒ 手机/平板经局域网连本机 Agent 的路径一并没了。
  若将来要开 LAN，必须先做凭据（用户可输入的口令 + cookie/Basic），不能只开开关
- 模型面板的用户要先会用 `models.json`（或先跑一次 CLI 登录），这是排除登录能力的直接代价，
  必须在面板上给出明确指引，否则用户会卡在「一个模型都没有」
- 子代理延后期间，模型无法委派子任务（除非用户装了扩展）；侧栏不会把子代理会话聚簇到宿主下
- `bash-output` 不做 ⇒ 超长 bash 输出在 Web 端只能看到截断部分（`.jsonl` 里引用的是临时文件）
- 「延后」意味着后续会重开：重开时须走新 ADR，并同步更新本文的状态（不得只改代码）
